# Шаг 1. Постановка: отображение классов в действия

**Задание.** Описать модальность входа, выход модели и **полное** отображение «класс →
действие» (например, `forward → linear.x = 0.3`). Объяснить, почему задача годится для
управления роботом. **Не меньше трёх различных действий.**

## Что сделано

**Вход** — видеопоток камеры, смотрящей на кормушку. В демонстрации это видеофайл
собственной съёмки (`DSCN2701.MOV`, по номеру соответствует проверочному клипу
`kormushka2701`), 5 кадров в секунду по кругу. Живая камера подключается тем же узлом:
`source:=0`.

**Выход модели** — вероятности трёх классов: `feeding`, `alert`, `empty`.

**Смысл робота** — наблюдатель, который подбирается к птице, не спугнув её.

**Отображение** — таблица `MOVE` в `controller_node.py`, сообщение `geometry_msgs/Twist`:

| действие | когда уместно | `linear.x`, м/с | `angular.z`, рад/с |
|---|---|---|---|
| `approach` — подъехать | птица кормится | 0.20 | 0.0 |
| `hold` — стоять | птица осматривается | 0.00 | 0.0 |
| `retreat` — отъехать с разворотом | птицы нет | −0.15 | 0.6 |
| безопасная команда | уверенность решения ниже порога | 0.00 | 0.0 |

Три различных действия плюс безопасная команда.

**Почему задача годится для управления.** Правильное действие зависит от состояния сцены,
а цена ошибки асимметрична: подъехать к насторожившейся птице хуже, чем лишний раз
постоять. Поэтому выбор действия — не таблица «класс → действие», а решение с учётом
неуверенности модели (шаг 6). Класс — свидетельство о сцене, а не приказ.

## Что показала работа

Задуманное отображение («кормится → подъехать, осматривается → стоять, пусто →
отъехать») на итоговой модели не выполняется буквально: модель не выдаёт `feeding`.
Контроллер, знающий об этом из матрицы ошибок, подъезжает на `alert`. Разбор — шаг 6.
