## Архитектура

```
   веб-камера / клип
          │
          ▼
  ┌────────────────┐   sensor_msgs/CompressedImage
  │camera_publisher│ ──────── /image/compressed ────────┐
  └────────────────┘                                    │
                                                        ▼
                                              ┌──────────────────┐
                                              │ classifier_node  │
                                              │  onnxruntime     │
                                              └──────────────────┘
                                                        │
                                        std_msgs/String │ /model_result
                                        {label, probs,  │
                                         confidence,    ▼
                                         latency_ms}  ┌──────────────────┐
                                                      │ controller_node  │
                                                      │ argmin G(u)      │
                                                      └──────────────────┘
                                                                │
                                              std_msgs/String   │ /action
                                              {action, risk,    ▼
                                               ambiguity, G}  ┌────────────┐
                                                              │  Gradio    │
                                                              └────────────┘
```

**Два решения, которые надо назвать в отчёте, а не умолчать.**

*Почему `CompressedImage`, а не `Image`.* Обычный `sensor_msgs/Image` требует
`cv_bridge`, которого в свежей установке ROS 2 часто нет и который тянет за собой
сборку. `CompressedImage` заполняется двумя строками через `cv2.imencode`, и кадр
идёт по шине уже сжатым. Меньше зависимостей и меньше трафика.

*Почему `std_msgs/String` с JSON, а не своё сообщение.* Своё `.msg` потребовало бы
отдельного пакета интерфейсов и сборки через `rosidl`. На этом масштабе это лишняя
деталь, а JSON читается глазами прямо в `ros2 topic echo /model_result`. Это
осознанное упрощение, а не незнание — так и надо написать.

## Контроллер: почему не порог

В чек-листе значится «контроллер с порогом уверенности». Порог — три строки. Вместо
него действие выбирается **минимизацией ожидаемой свободной энергии** по трём
действиям: подъехать · стоять · отъехать.

```
G(u) = риск + неоднозначность

риск           = KL( Q(o|u) ‖ P(o) )     насколько исход разойдётся с желаемым
неоднозначность = E_{Q(s|u)} H[ A(·|s,u) ]  насколько исход будет неинформативен
```

Порог никуда не девается — он **выводится** из предпочтений `C` и переходов `B`, а не
назначается руками. Это ровно то, что предлагалось в плане: требование выполняется
строго сильнее.

**Одна деталь, без которой конструкция не работает.** Я сначала написал модель, где
правдоподобие `A` одинаково для всех действий, — и контроллер стал всегда отъезжать.
Логично: если подъезд ничего не даёт, а только пугает птицу, зачем подъезжать.

Починка содержательная: **правдоподобие зависит от действия**. Вблизи птица занимает
больше кадра и классификатор точнее, издали — хуже (`SHARP` в `efe.py`). Тогда
появляется настоящий выбор между двумя вещами: подъехать и увидеть лучше, но спугнуть,
или остаться и знать хуже. Это и есть прагматика против эпистемики — то самое, что
панель показывает отдельной таблицей.

Как ведёт себя готовый контроллер:

| сцена | действие | почему |
|---|---|---|
| птица спокойно кормится | **подъехать** | неоднозначность падает втрое, риск ещё терпимый |
| птица насторожилась | **стоять** | подъезд резко повышает риск спугнуть |
| кормушка пуста | **отъехать** | пугать некого, но и смотреть не на что |
| модель не уверена | **стоять** | самое дешёвое действие, пока не прояснится |

Четыре сцены — три разных действия. Для записи демо этого достаточно.

**Запасной вариант на день демонстрации.** Если с активным выводом что-то пойдёт не
так — `-p mode:=threshold`, и контроллер становится обычным порогом. Требование
чек-листа выполняется буквально, а абзац про свободную энергию просто уходит в
«дальнейшую работу». Бонус не может стать блокером.

**Матрица ошибок вместо выдуманных чисел.** Предпочтения `C` и переходы `B` заданы
руками — это про то, чего мы хотим, их измерить нельзя. А вот `A` — надёжность
классификатора — берётся из настоящей матрицы ошибок:
`-p confusion:=results/small.json`. Это то, что отличает работающую модель от красивой.

## Порядок запуска

### 1. Экспорт и валидация (шаг 5 плана)

```bash
pip install ultralytics onnx onnxruntime opencv-python
python export_onnx.py --weights runs/classify/small/weights/best.pt \
                      --data data/birds_v1_course3
```

Печатает и кладёт в `results/onnx_validation.json`:

- максимальное расхождение вероятностей PyTorch против ONNX,
- сколько кадров изменили предсказанный класс (должно быть 0),
- задержку обоих, медиану и 95-й перцентиль, и кадры в секунду.

**Эти числа идут в отчёт.** Норма для расхождения — порядка 1e-5…1e-4. Если больше
1e-2 или хоть один класс изменился — писать честно и разбираться, а не прятать.

### 2. Сборка пакета ROS 2

```bash
cp -r ros2_ws/src/birdcls ~/ros2_ws/src/
cd ~/ros2_ws
colcon build --packages-select birdcls
source install/setup.bash
```

### 3. Запуск

Всё разом:

```bash
ros2 launch birdcls demo.launch.py model:=/полный/путь/best.onnx source:=0
```

Или по узлам, в трёх терминалах — так нагляднее для записи:

```bash
ros2 run birdcls camera_publisher --ros-args -p source:=0 -p fps:=5.0
ros2 run birdcls classifier_node  --ros-args -p model:=best.onnx
ros2 run birdcls controller_node  --ros-args -p confusion:=results/small.json
```

Проверка топика — это тот пункт чек-листа, где надо показать `/model_result`:

```bash
ros2 topic echo /model_result
ros2 topic hz /model_result
ros2 node list && ros2 topic list
```

### 4. Панель

```bash
python gradio_panel.py --mode ros
```

Если ROS не поднялся — тот же вид без него:

```bash
python gradio_panel.py --mode local --model best.onnx --source 0
```

Панель показывает кадр, три вероятности, выбранное действие и **таблицу разложения
решения на риск и неоднозначность**. Последнее — то, что делает демо продуманным.


## Файлы

```
export_onnx.py                     экспорт + валидация + задержка
gradio_panel.py                    панель, оба режима
ros2_ws/src/birdcls/
  package.xml, setup.py            метаданные пакета
  launch/demo.launch.py            все три узла разом
  birdcls/camera_publisher.py      камера или файл → /image/compressed
  birdcls/classifier_node.py       onnxruntime → /model_result
  birdcls/controller_node.py       argmin G → /action
  birdcls/efe.py                   модель POMDP: A, B, C, G. Общая для узла и панели

Рядом, в project1/step3_annotation_versioning/:
  to_cvat.py                       разметка → формат CVAT и Roboflow, без переразметки
  README_CVAT.ru.md                как закрыть пункт про CVAT за десять минут
```

`efe.py` — это тот же формализм, что в `active_inference_forager.py` из научной части,
только с тремя состояниями вместо решётки. В отчёте на это стоит сослаться: одна и та
же конструкция обслуживает и симуляцию агента, и контроллер робота.
